《智能座舱测试策略从规划到执行》

22、兼容性测试：不同硬件平台、不同Android版本、不同分辨率

兼容性测试，说白了就是让你的座舱应用在五花八门的硬件上都能跑得顺。高通、瑞萨、恩智浦，这三家芯片我几乎都打过交道。每个平台都有自己的脾气，稍不留神就给你来个闪退或者黑屏。

我个人习惯把兼容性测试分成三个维度：硬件平台、系统版本、屏幕分辨率。这三个维度排列组合起来，测试矩阵会非常庞大。但你想想看，真正需要全覆盖的其实只有核心功能，边缘场景可以靠策略去覆盖。

硬件平台差异：高通、瑞萨、恩智浦

这三家芯片的架构和驱动栈差异很大。我在项目中遇到过同一个手势动画在高通上丝滑流畅，换到瑞萨上就掉帧卡顿。为什么会这样？因为GPU的渲染管线不一样，驱动对OpenGL ES的支持程度也不同。

平台 GPU 典型问题 测试重点
高通骁龙 Adreno系列 纹理压缩格式不兼容 3D渲染、视频解码
瑞萨R-Car PowerVR/Rogue Shader编译慢、UI卡顿 动画帧率、多窗口切换
恩智浦i.MX Vivante GC 内存带宽不足、合成延迟 SurfaceFlinger性能、HWC
注意： 恩智浦平台的内存带宽通常只有高通的60%-70%。如果你的应用大量使用GPU合成，在i.MX上很容易出现掉帧。我曾经因为一个模糊效果没做降级处理，导致在恩智浦上直接黑屏。

Android版本碎片化

座舱里的Android版本跨度很大。有的车厂还在用Android 10，有的已经上了Android 14。每个版本对权限、后台服务、多窗口的支持都不一样。

我建议你重点关注这几个版本差异：

  • Android 10-11： 分区存储、后台位置权限收紧。很多地图应用在这上面崩溃过。
  • Android 12： 多窗口模式大改，分屏比例从50:50变成了自由调整。你的布局能自适应吗？
  • Android 13-14： 前台服务类型必须声明，通知权限默认关闭。很多音乐应用第一次启动时弹不出通知。
小技巧： 用adb shell getprop ro.build.version.sdk快速获取系统API等级。我习惯在CI脚本里加一个循环，把同一个APK刷到不同版本的模拟器上跑冒烟测试。

分辨率与DPI适配

座舱屏幕的分辨率五花八门。从1280x720到3840x2160都有。更麻烦的是DPI，有的屏幕是160dpi，有的是320dpi，甚至还有非标准值。

我记得有一次，一个按钮在1920x1080的屏幕上显示正常，换到1280x720的屏幕上就跑到屏幕外面去了。查了半天，发现是布局里用了硬编码的px值，没有用dp。

// 错误写法：硬编码像素
button.setWidth(200); // px

// 正确写法：使用dp
button.setWidth(dp2px(200)); // dp转px

// 工具函数
public static int dp2px(float dp) {
    return (int) (dp * Resources.getSystem().getDisplayMetrics().density + 0.5f);
}
核心原则： 所有尺寸都用dp/sp，图片用多套切图（mdpi/hdpi/xhdpi/xxhdpi）。如果屏幕DPI不是标准值，系统会自动缩放，但缩放后的效果一定要人工确认。

兼容性测试矩阵设计

测试矩阵不能盲目全量覆盖。我一般按这个优先级来排：

  1. P0： 主流平台+最新Android版本+主流分辨率（高通+Android 13+1920x1080）
  2. P1： 瑞萨/恩智浦+Android 12+1280x720
  3. P2： 其他组合，按市场占有率排序

每个组合至少跑一遍全功能回归。如果时间不够，P2组合只跑核心功能（导航、音乐、电话、设置）。

自动化兼容性测试

纯手工测兼容性太累了。我建议用云真机平台或者自建机柜。每个平台刷好对应的系统镜像，用脚本批量安装APK并执行UI自动化。

这里有个坑：不同平台的adb驱动可能不一样。恩智浦的板子有时候adb连不上，需要手动装驱动。我曾经因为这个浪费了一整天。

# 批量安装APK到所有设备
for device in $(adb devices | grep -w device | awk '{print $1}'); do
    adb -s $device install -r app-release.apk
    adb -s $device shell am start -n com.example/.MainActivity
    sleep 5
    adb -s $device shell screencap /sdcard/screenshot.png
    adb -s $device pull /sdcard/screenshot.png ./results/$device.png
done
经验之谈： 兼容性测试不是一次性的。每次系统OTA升级、每次芯片驱动更新，都要重新跑一遍。我习惯在CI里设置每周定时任务，自动触发兼容性测试并生成报告。

常见兼容性Bug清单

  • SoC特定崩溃： 某个API在高通上正常，在瑞萨上返回null。比如Camera2 API的某些特性。
  • 版本兼容问题： Android 10上能用的权限声明，在Android 14上被废弃了。编译时targetSdkVersion没更新就会出问题。
  • 分辨率适配问题： 图片拉伸变形、文字被截断、触摸区域偏移。尤其是非标准比例屏幕（比如车规级的长条屏）。
  • 多屏交互问题： 座舱通常有中控屏、仪表屏、HUD。不同分辨率下多屏联动是否正常？
避坑指南： 我曾经在瑞萨平台上遇到一个诡异问题：应用启动时白屏5秒。查了三天发现是SurfaceFlinger的硬件合成器(HWC)不支持某种图层格式。最后只能降级到GPU合成，虽然帧率降了但至少能用了。所以，兼容性测试一定要在真机上跑，模拟器永远发现不了这种问题。
