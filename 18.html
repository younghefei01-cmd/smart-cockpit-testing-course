《智能座舱测试策略从规划到执行》

18、CI/CD集成：Jenkins/GitLab CI流水线、测试用例自动触发、Allure报告、质量门禁

说实话，很多团队做智能座舱测试，卡就卡在「手工跑一遍太慢」上。你想想看，一个座舱项目，光HMI的测试用例就上千条，每次提测都要人工去点、去等、去截图，然后整理报告……等结果出来，开发那边代码都改了三轮了。

我经历过一个项目，前期全靠手工，每次回归测试要两天。后来我把CI/CD流水线搭起来，测试用例自动触发，Allure报告自动生成，质量门禁一卡——回归时间从两天压缩到40分钟。嗯，今天我们就聊聊这件事。

18.1 为什么座舱测试需要CI/CD？

智能座舱的软件迭代速度非常快。今天加个语音功能，明天改个空调面板布局，后天修个蓝牙连接bug。如果没有自动化流水线，测试永远在追开发，永远追不上。

CI/CD能帮你解决三个核心问题：

  • 频率问题：每次代码提交都能自动触发测试，不用等人安排
  • 一致性问题：每次跑的测试环境、测试步骤、测试数据都一样，不会出现「我本地能过，你那边就挂」
  • 反馈问题：测试结果实时可见，开发提交代码后半小时就知道自己有没有搞坏东西

核心观点：CI/CD不是锦上添花，而是座舱测试的「基础设施」。没有它，自动化测试的价值至少打五折。

18.2 流水线架构：Jenkins vs GitLab CI

目前主流的选择就两个：Jenkins和GitLab CI。我两个都用过，说说我的感受。

对比维度 Jenkins GitLab CI
部署方式 独立部署，需要维护Jenkins Server 集成在GitLab中，开箱即用
配置方式 Web界面 + Jenkinsfile .gitlab-ci.yml 纯代码配置
插件生态 非常丰富，几乎什么都能做 相对精简，但够用
学习成本 中等，Pipeline语法需要熟悉 较低，YAML配置直观
适合场景 复杂流水线、多工具链集成 GitLab深度用户、中小团队

我个人习惯：如果团队已经在用GitLab，直接用GitLab CI就够了，省去维护Jenkins的精力。如果团队工具链复杂，比如要同时对接Jira、SonarQube、私有仓库等，Jenkins的插件生态更友好。

18.3 测试用例自动触发策略

流水线搭好了，接下来就是「什么时候跑什么测试」。这里有个常见的坑——我见过有人把所有测试用例都放在一个流水线里跑，结果一次提交要等两个小时。这其实没必要。

我建议按触发条件分层：

  • 提交触发（Commit）：只跑冒烟测试和单元测试。5分钟内出结果，告诉开发「基本功能没炸」。
  • 合并请求触发（MR/PR）：跑全量接口测试和核心HMI测试。15-20分钟出结果，告诉开发「合并后不会搞坏主干」。
  • 定时触发（Nightly）：跑全量回归测试，包括压力测试、稳定性测试、多语言测试。晚上跑，第二天早上看报告。

经验之谈：我曾经把全量回归放在每次提交时跑，结果开发怨声载道，因为等结果的时间比写代码还长。后来改成MR触发+Nightly全量，大家终于不骂我了。

下面是一个GitLab CI的简化配置示例，展示如何按分支和触发条件区分测试阶段：

stages:
  - smoke
  - integration
  - regression

smoke_test:
  stage: smoke
  script:
    - python run_smoke.py
  only:
    - branches
  except:
    - main

integration_test:
  stage: integration
  script:
    - python run_integration.py
  only:
    - merge_requests

regression_test:
  stage: regression
  script:
    - python run_regression.py
  only:
    - schedules
  when: nightly

18.4 Allure报告：让测试结果一目了然

测试跑完了，报告怎么给？我见过有人把测试日志直接贴到群里，几百行日志，谁看谁头疼。

Allure是我用过最顺手的测试报告框架。它能把测试结果组织成可交互的HTML页面，有趋势图、有失败详情、有截图附件。开发点开一看，就知道自己哪里写崩了。

集成Allure其实就三步：

  1. 测试框架接入：在pytest或JUnit中配置Allure适配器，添加@allure.feature、@allure.story等装饰器
  2. 流水线生成报告：测试执行后，调用allure generate命令生成HTML报告
  3. 报告归档/发布：将报告上传到GitLab Pages或Jenkins的HTML Publisher插件

举个例子，在GitLab CI中集成Allure：

allure_report:
  stage: report
  script:
    - allure generate allure-results --clean -o allure-report
  artifacts:
    paths:
      - allure-report
    expire_in: 30 days

注意：Allure报告中的附件（截图、日志）会占用大量存储空间。我建议设置artifacts的过期时间，比如30天自动清理，否则CI服务器的磁盘很快会被撑爆。

18.5 质量门禁：守住底线

流水线跑完了，报告也生成了，然后呢？如果测试失败了，代码该不该合入？

质量门禁就是干这个的。它是一组规则，自动判断本次提交是否「达标」。不达标就拦住，不让合并。

我常用的门禁规则：

  • 冒烟测试通过率100%：有一条冒烟用例失败，直接拒绝合并
  • 核心接口测试通过率≥95%：允许少量非关键失败，但核心功能不能崩
  • 新增代码覆盖率≥80%：防止开发为了通过测试而「跳过」测试
  • 无P0/P1级缺陷：如果有严重缺陷，必须修复后才能合入

在GitLab CI中，可以通过allow_failure和when: manual来实现柔性门禁：

quality_gate:
  stage: gate
  script:
    - python check_quality_gate.py
  only:
    - merge_requests
  allow_failure: false  # 门禁失败，MR无法合并

我的建议：质量门禁不要一开始就设得太严。我见过一个团队，上来就要求覆盖率90%，结果开发天天跟测试吵架。先设一个「及格线」，比如70%，等团队适应了再逐步提高。门禁的目的是守住底线，不是制造对立。

18.7 避坑指南

最后，分享几个我踩过的坑：

  • 别把CI服务器当开发机用：我见过有人在CI上装了一堆依赖，结果每次构建都要下载半小时。把依赖缓存起来，或者用Docker镜像固化环境。
  • 测试数据要独立：多个流水线同时跑的时候，如果共用一套测试数据，会出现「互相干扰」的情况。每个流水线用独立的测试账号和数据快照。
  • 门禁失败要有人跟进：门禁拦住了，但没人去修，那门禁就形同虚设。我建议门禁失败后自动在Jira或GitLab上创建Bug，并@对应的开发。
  • 报告要可追溯：每次构建的Allure报告要保留历史版本，方便对比「这次比上次多了哪些失败」。我习惯在报告页面加上构建号和时间戳。

一个小技巧：在Allure报告中添加自定义环境信息，比如座舱的硬件版本、系统版本、屏幕分辨率。这样看到失败用例时，能立刻知道是在什么环境下复现的，省去很多沟通成本。

好了，CI/CD集成这部分就聊到这儿。流水线搭好了，测试用例自动跑了，报告自动出了，门禁也卡住了——你会发现，整个团队的节奏都变了。开发敢频繁提交了，测试不用熬夜跟版本了，项目经理也能实时看到质量状态了。这才是智能座舱测试该有的样子。
