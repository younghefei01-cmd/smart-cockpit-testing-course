《智能座舱测试策略从规划到执行》

17、自动化测试框架：Python + pytest + Appium/UI Automator、关键字驱动、数据驱动、Page Object模式

说实话，自动化测试框架这个话题，很多团队都踩过坑。我见过不少项目，测试代码写了一堆，结果换个车型、改个分辨率就跑不起来了。为什么？因为框架选型没想清楚，代码耦合太严重。

今天咱们就聊聊，在智能座舱这个场景下，怎么搭一套真正能用的自动化框架。核心就四个字：分层、解耦。

17.1 技术栈选型：为什么是 Python + pytest + Appium？

先说说我的选择逻辑。Python 不用多讲，生态好、上手快，测试团队里基本没人不会。pytest 呢，比 unittest 灵活太多，fixture、参数化、插件机制，写起来很舒服。

Appium 这边，很多人觉得它只是用来测手机 App 的。其实不然。智能座舱的中控屏、仪表盘，本质上就是个 Android 系统（或者 QNX 跑 Android 虚拟机）。Appium 通过 UI Automator 跟底层通信，能直接操作界面元素。

我的经验： 别一上来就追求全量自动化。我习惯先挑 20% 的高频回归用例做试点，跑通了再铺开。这样团队有信心，框架也能逐步打磨。

这里有个对比表，帮你快速理解各层的关系：

层级 技术组件 职责
脚本层 Python + pytest 用例编排、断言、报告生成
驱动层 Appium / UI Automator 设备通信、元素定位、手势操作
模式层 Page Object + 关键字驱动 页面抽象、操作封装、数据分离

17.2 Page Object 模式：让代码不再“牵一发动全身”

Page Object 模式，说白了就是把每个页面封装成一个类。页面上的元素、操作方法，都放在这个类里。测试用例只跟 Page Object 打交道，不直接碰 Appium 的 API。

为什么要这么做？你想想看，座舱的 UI 迭代多频繁啊。今天这个按钮换个 ID，明天那个列表改个布局。如果测试代码里到处都是 find_element_by_id，改起来得疯掉。

我给大家看个例子：

# 主页 Page Object
class HomePage:
    def __init__(self, driver):
        self.driver = driver

    # 元素定位集中管理
    _nav_button = (By.ID, "com.example:id/nav_btn")
    _volume_slider = (By.ID, "com.example:id/volume_slider")

    def click_nav(self):
        self.driver.find_element(*self._nav_button).click()

    def set_volume(self, level):
        slider = self.driver.find_element(*self._volume_slider)
        # 滑动操作封装
        ActionChains(self.driver).click_and_hold(slider).move_by_offset(level, 0).release().perform()
核心原则： 一个 Page Object 只对应一个页面。如果页面有多个 Tab 或弹窗，可以拆成子 Page Object。别把整个 App 塞进一个类里，那比没有模式还糟糕。

17.3 关键字驱动：让业务人员也能写用例

关键字驱动，其实就是把测试步骤抽象成“关键字”。比如“点击”、“输入”、“滑动”、“等待”。每个关键字对应一个函数。测试用例就变成了一张关键字表格。

我个人习惯把关键字分成三层：

  • 基础关键字： 点击、输入、获取文本、滑动
  • 业务关键字： 打开导航、调节音量、切换驾驶模式
  • 复合关键字： 登录流程、导航到目的地、播放音乐

举个例子，一个“调节音量到 50%”的用例，用关键字表格写出来就是：

步骤 关键字 参数
1 打开设置面板 无
2 滑动音量条 50
3 验证音量显示 50%
避坑指南： 我曾经在一个项目里把关键字粒度拆得太细，结果一个“点击”就写了 5 个关键字（点击按钮、点击文本、点击坐标...）。后来发现维护成本反而更高。记住：关键字粒度以“业务可理解”为准，别为了抽象而抽象。

17.4 数据驱动：一套脚本跑遍所有车型

数据驱动，就是把测试数据从代码里抽出来，放到外部文件里（Excel、YAML、JSON 都行）。pytest 的 @pytest.mark.parametrize 天然支持这个模式。

座舱测试里，数据驱动特别适合做“多车型兼容”。比如不同车型的屏幕分辨率不同，按钮位置不同。你只需要维护一套 Page Object，然后给每个车型配一套定位数据。

# 数据文件：car_data.yaml
Model_S:
  resolution: [1920, 720]
  nav_button: "com.example.model_s:id/nav_btn"
  volume_slider: "com.example.model_s:id/volume_slider"

Model_X:
  resolution: [2560, 1440]
  nav_button: "com.example.model_x:id/nav_btn"
  volume_slider: "com.example.model_x:id/volume_slider"

# 测试用例
@pytest.mark.parametrize("car_model", ["Model_S", "Model_X"])
def test_volume_control(car_model, load_car_data):
    data = load_car_data[car_model]
    home = HomePage(driver, data)
    home.set_volume(50)
    assert home.get_volume() == "50%"

你看，测试逻辑完全没变，换车型只需要换数据文件。这就是数据驱动的威力。

17.6 落地建议：从 0 到 1 怎么走

框架搭好了，怎么落地？我建议分三步走：

  1. 先搭骨架： 选一个最简单的页面（比如主页），实现 Page Object + 一个关键字。跑通端到端流程。
  2. 再填血肉： 逐步覆盖核心功能页面。每个页面只封装最常用的 3-5 个操作。别贪多。
  3. 最后上数据： 等 Page Object 稳定了，再引入数据驱动。先做 2 个车型的对比，验证框架的扩展性。
一个小技巧： 我习惯在 pytest 的 conftest.py 里放 fixture，统一管理 driver 的初始化和清理。这样每个用例都不用关心设备连接的问题，专注写业务逻辑。

嗯，框架这部分内容比较多，但核心就一句话：分层解耦，数据分离。你只要把 Page Object、关键字驱动、数据驱动这三块理清楚，后面不管接什么车型、什么屏幕，改起来都很快。
